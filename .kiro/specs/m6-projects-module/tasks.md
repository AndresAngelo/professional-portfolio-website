## Overview

This file defines the 10-goals skeleton for M6. Individual task detail (~10 tasks per goal) is generated by Stage 3 (Google AI Studio) into separate `goal1.md`–`goal10.md` files in this directory.

Each task in the generated goal files must be fully self-contained for stateless orchestrator execution (Nomic retrieval, gemma-3-1b router, gemma-4-e2b executor, router audit). No inter-task conversation history is assumed.

M6 delivers the Projects module: the index route `/projects` (`SCR-02`), the detail route `/projects/[slug]` (`SCR-03`), eleven presentational components and one client island (`ProjectsExplorer`) in `src/components/projects/`, and pure helpers in `src/lib/projects/` for filter parsing, filtering, option derivation, related-project selection, link selection, heading demotion, result-count text, and metadata. M6 composes M2 loaders, M3 primitives, the M4 shell, and the M5 `formatDisplayDate` and `compareStrings` without modifying them. `ProjectsExplorer` is the only `'use client'` module and the only caller of `useSearchParams`.

## Notes

### Cross-Goal Notes

- **One client island:** `ProjectsExplorer` is the only `'use client'` module and the only `useSearchParams` caller. All other components are plain; `ProjectFilterBar`, `ProjectGrid`, and `ProjectCard` join the client bundle only as the Explorer's children.
- **URL is the filter state:** The Explorer derives filters from `useSearchParams()` each render and writes with `router.replace(..., { scroll: false })`. No duplicate state. Only `useRouter` and `useSearchParams` are mocked in tests.
- **Static HTML is complete:** The `Suspense` fallback is the unfiltered `ProjectGrid`, so `/projects` contains every card without JavaScript. The filter bar appears only after hydration.
- **Serializable client props:** The Explorer receives `ProjectCardData` only. `documentation`, tags, metrics, and URLs never cross to the client.
- **One technology key:** `techKey` (trim, `toLowerCase`) is the single comparison used for deduplication, parsing, filtering, and related selection.
- **One encoding path:** `serializeProjectFilters` is defined as `mergeFiltersIntoQuery('', f)`.
- **Heading levels:** `ProjectCard` takes `headingLevel` (2 on the index, 3 in related projects). Documentation headings pass through `demoteHeadings`.
- **Reuse, do not recreate:** `formatDisplayDate` and `compareStrings` come from M5. If either is missing, G1.T7 stops and escalates; M6 writes nothing outside its four locations.
- **Scope guard:** M6 edits only `src/app/projects/`, `src/components/projects/`, `src/lib/projects/`, and `tests/`. Missing primitives, tokens, or dependencies are recorded in `task-notes.md` and escalated (`AGENTS.md` 6.2), never patched.
- **Deferred verification:** Layout, overflow, touch targets, contrast, and layout shift are not evaluated by jsdom and are covered by the manual list (layout shift measurement is M9).

### Testing Patterns

- Property tests use `fast-check` (no hand-rolled generators), at least 100 runs each, and a tag comment: `Feature: m6-projects-module, Property N: <text>`.
- Render-based property tests call `cleanup()` between iterations and use bounded array sizes.
- Explorer tests use the store-backed `next/navigation` mock in `tests/projects/helpers/mock-navigation.ts`; `replace` writes into the store so `useSearchParams` reflects it.
- Loaders are mocked with `vi.mock` using fixtures from `tests/fixtures/projects-data.ts`.
- Date tests set `process.env.TZ` per case; purity tests use deeply frozen inputs.
- jsdom does not evaluate Tailwind; CSS layout, overflow, touch targets, and contrast are covered by the manual verification list.
